Differences between `SP-16_DJS-1000_project_format_spec.md` and the fixtures, decisions taken while building, and the unverified behaviour the code relies on. Evidence labels follow the spec: **Confirmed (file)**, **Confirmed (SP-16)**, **Reported**, **Unverified**.

Last updated 2026-10-11.

`Fixtures/audio/` holds generated sound for the input formats, not SP-16 files: `tone16.wav` and `tone24.wav` come from `make_audio_fixtures.py` in the same folder, and macOS `afconvert` made the AIFF and AIFF-C files from them (`-f AIFF` or `-f AIFC`, `-d BEI16` or `-d BEI24`) and the FLAC files (`-f flac -d flac`, Apple's encoder, 4608-sample blocks, MD5 stored). `tone16.m4a` and `tone16.alac.m4a` are from `afconvert` too (`-f m4af -d aac -b 256000`, and `-d alac`): a song in an MP4 by itself, not a stem file. The MP3 files are from LAME: `lame -b 128` (`tone16.mp3`), `-V 2` (`tone16.vbr.mp3`) and `-b 320` (`tone16.320.mp3`). Each file is checked against the WAV named by the part of its name before the first dot. `afconvert` cannot write little-endian (`sowt`) AIFF-C, so that variant is built by hand in the tests.

Not available: `one.tpkg`, `02`, `03`, `06`, `07`. `empty.tpkg` appears to be the loader's package under another name.

Every project parses with all bytes consumed and re-emits an identical payload, including the project inside each package.

## 2. Where the fixtures differ from the spec

1. **`ArrangementData0` is not SP-16 only.** The DJS-1000 files and the loader files all carry it, with `length` 0 and 999 default records. The spec's tree marks it SP-16 only. (Confirmed, file.)
2. **Loader projects have a shorter `RoutingData`.** `baked_example.prj` and `empty.tpkg` have three scalars (`assignMode`, `headphoneOutCh`, `effectMode`); unit-saved files have seven. (Confirmed, file.)
3. **There is no file numbered arr1.** `arr0-one-section.prj` fills that slot. Its internal `projectFilePath` still says `arr0.prj`, because it was saved on the unit under that name and renamed afterwards. `arr0.prj` itself is the true empty baseline.
4. **The arranger switch is independent of the section list.** `arr0-one-section` to `arr6` hold one section with `bPlayArrangement` false; it is true from `arr7` to `arr12`. (Confirmed, file.)
5. **The loader's zip differs from `rev1`'s.** `empty.tpkg` has DOS dates with month and day 0, sets the UTF-8 flag (0x800) and needs version 1.0. `rev1.tpkg` has 1980-01-01, no flags, version 2.0, made-by 0x0314 and external attributes 0x01A40000. The writer copies `rev1`, the form confirmed on the SP-16.
7. **`nGrids` is the slice count.** The spec said it was not. Setting 8 slices on the unit changed `nGrids` from 16 to 8 and nothing else; with a point moved, `grids` holds `nGrids + 1` boundaries from 0 to the sample length. The baseline for these saves (`slice1-no-slice.tpkg`, not kept because it carries the sample) already had 16 with no slicing done, because it was built by the loader page, whose template has 16 on all 256 pads (as do `baked_example.prj` and the DJS-1000 file `04.prj`). The SP-16's own empty project (`arr0.prj`, the export template) has 1 on every pad, so an export must set it. (Confirmed, file.) The spec's entry was rewritten.
6. **`08.prj` has mixed choke groups** on its four stems (-1, 7, 1, 0), apparently left over from testing.

## 3. Details the spec leaves out

All Confirmed (file).

- An empty string scalar is `05 00` (type 5 and the terminator), not a null scalar.
- A bool array such as `TrackMutes` is `07`, `vi(count)`, then one item per value, each `01 03` (length 1, type false) or `01 02`.
- The `.dat` file is a bare tree with no container wrapper, 68 bytes for a typical sample.
- The unit-saved template already has `chokeGroup` -1, `stretchMode` `Off` and `bLoop` false on every pad. `rev1` changed only `lengthSample` and `audioSourceUrl` per pad.
- The full set of changes from `arr0.prj` to `rev1.prj` is: `bPlayArrangement`, `projectFilePath`, scene `name`, the inserted `PatternData<N>`, each pad's `lengthSample` and `audioSourceUrl`, the scene's routing, and the arrangement. `projectBpm` was left at 120.
- **Velocity** is `AmpEnvelopeData.bVelocityEffective`, a bool, false on every pad of every unit-saved file until `velocity.prj`, where tracks 1 and 2 of scene 1 have it true. Nothing else in that file changed but the sample paths, which the unit rewrites when it imports a package's samples (`$Int0/%Tmp/...` to `$Int0/%Smp/[Imported]/<project>/...`). Strands sets it by stem from the Export page (2026-10-16). With it on, a pattern's triggers, which keep the unit's default step entries, play at the same level as without (Confirmed, SP-16, 2026-10-16: `U18Velocity.tpkg`, D21).
- `arr8-length.prj` has triggers on pad 5 at steps 9, 25 and 62 with `Length` 21, confirming that steps past `Length` stay in the file.
- `patternQuantizeUnit` is 1048577 (0x100001) and `padQuantizeUnit` is 65540 (0x10004) in every file. Still not decoded.
- Python's `zlib` at level 6 reproduces every `Sections` and `Steps` blob in the SP-16 fixtures byte for byte. Whether Unity's `DeflateStream` does has not been checked; the tests compare blobs by inflated content, which is all the unit needs.

## 4. Decisions

| Decision | Reason |
| --- | --- |
| Everything runs inside Unity, as assemblies with no engine references and NUnit Edit Mode tests | The user's preference; replaces the kickoff's `netstandard2.1` library and `net8.0` xUnit projects |
| No standalone `sp16` tool; commands are Editor menu items and static methods callable through the CLI bridge | Follows from the above |
| The zip container is written by hand | Guarantees stored entries and the exact header fields of `rev1.tpkg`; lets entries be written one at a time |
| The template is passed to the library as bytes | Keeps the library free of Unity resource loading |
| Patterns are written with scalars in the unit's order (`Steps`, `Length`, `TrackMutes`, `TrackSolos`) | The unit's order is the safe choice; `rev1` used another order and loaded |
| First milestone is one WAV to one package, with the beat grid estimated from the audio | Agreed with the user; the kickoff had no analysis in its first two milestones |
| Chunks are 4 bars, one pad and one pattern each, repeat 1 | Uses only behaviour confirmed on the unit and avoids the unknown length of an empty pattern |
| Consecutive chunks overlap with a 5 ms linear crossfade (`WavExportOptions.CrossfadeMs`) | Not in the original plan. A trigger that lands slightly early or late blends rather than gapping or clicking |
| Audio at another sample rate is converted to 44.1 kHz as it is loaded (`Resampler`) | The user's request (2026-10-11). The unit is still given 44.1 kHz files and `stretchMode` stays `Off`: the rule against stretching is about playback on the unit, not about bringing a file to the unit's rate |
| Routing is left at the template default for a full mix, and for layers that are on master | Both play from the master output, which is where the template has every pad. Only an export with layers on other outputs sets 8ch routing |
| With slicing on, every chunk, the lead-in included, gets a slice boundary on every beat line, written as explicit `grids` (`WavExportOptions.SliceOnBeats`, `ManualSliceFrames`) | Agreed with the user: 16 slices on a 4-bar chunk, playable from the pads. Explicit boundaries because a chunk is a little longer than 4 bars (the crossfade tail), so the unit's own equal division would drift late; they also allow points moved by hand. The app shows no slice controls: the user decided (2026-10-10) that slices on the beats need no attention, and dragging made every beat line a handle |
| Silence at the start of a file is left out, judged as more than 54 dB below the file's peak; a lead-in of under 30 ms after it is dropped (`WavExportOptions.TrimLeadingSilence`) | The user's request. Hiss before the music otherwise became a lead-in of nothing |
| Tempo is searched in one octave, 88 to 176 BPM (`BeatGridOptions`) | A tempo and its half or double cannot both be candidates |
| The audio before the first bar line becomes a first sample of its own, padded at the front with silence to a whole number of steps (`WavExportOptions.KeepLeadIn`) | The user needs the package to play from the very start of a file whose beginning is not on a bar line. Padding keeps the song's own tempo in every section, so nothing new depends on tempo precision |
| Grid lines are put on the front of the average hit, and the tempo is corrected from groups of eight beats matched against that average (`BeatProfiles`) | The first version placed lines from the steepest rise within 20 ms of each beat, which was about 20 ms late on the Traktor test recording |
| A chunk is made to start at an anchor, by default where the drums come in, and chunks are counted off both ways from it (`WavExportOptions.PatternAnchorSeconds`) | The user needs the drums to start a pattern after an intro of any length. The lead-in can therefore be up to just under 4 bars |
| A round tempo is taken when it fits the audio as well as the fitted one (`BeatGridOptions.PreferRoundTempo`) | The user's point: 119.993 is almost certainly 120. A tempo that is truly not round is kept, because the audio then fits it measurably better |
| Stems are exported as layers: a chunk is one sample per layer, on pads side by side, all triggered on step 1 by the chunk's pattern, and a scene holds 16 divided by the number of layers chunks (`WavToSp16.Plan` with `layers`, `StemsToSp16`) | Agreed with the user. The audio is cut exactly where a full mix is cut, so what is confirmed for a full mix carries over and only the start together is new |
| Every scene in use is set to 8ch with all 16 pads given an output, the layers' outputs repeating down the scene (`WavToSp16.PadOutputs`) | The spec says to set all 16 in 8ch mode. The same pattern in every scene keeps one layer in one column of pads |
| Stems that share an output, and are of one group, are added into one sample unless told to keep them apart, all of them (`mixSharedOutputs`) or one by one (`Stem.KeepApart`, which the app sets for every file on a strip marked "Keep as separate tracks"); a sum over full level is held at the limit and reported (`StemsToSp16.Prepare`) | Agreed with the user: it saves pads and sample memory. The user on 2026-10-10: "The option of mixing tracks together to save memory is a good one" |
| The grid for stems is the one with the most attack on its lines, out of those found from each stem alone and from all of them added together (`StemsToSp16.ChooseGrid`, `BeatDriftMeter.AttackOnLines`) | Agreed with the user as "analyse every stem and use the best fit". The stems together can be led by a part without drums; a stem alone can agree with itself at the wrong tempo. Measuring every grid against the whole song, over 4 ms either side of each line, separates them |
| A layer on a single output is written as mono files, its two sides added and halved (`ExportLayer.IsMono`, `WavToSp16.CutChunkMono`) | The user wants single outputs for mono tracks. What the unit does with the second side of a stereo sample on one output is not known, and a mono file leaves nothing to it. Halving keeps audio that is the same on both sides exactly as it was |
| The app can put every stem on the master output (`StripLayout.AllOnMaster`, `Sp16Output.Master`). Each strip is still a track of its own: files on one strip are mixed unless kept apart, and files on different strips never are, though they now share an output (`Stem.Group`, which is the strip). No strip is split and no sample is mono. It lies over what the strips are set to: turned off, a strip that was split is split again | The user's idea, 2026-10-11: "If users only want audio on the master channel they have to pile all their stems into one slot. I was thinking have a toggle that changes the slots and text from 1-2 etc to Master on all slots". With only the master connected, stems on the four pairs would give the first stem alone |
| Layers are all on master or none is; a mix of the two is refused (`WavToSp16.CheckOutputs`) | The unit's first mode could send some pads to master and others to 3-4, 5-6 or 7-8, but no generated project has tried it. Refused, so that nothing is guessed |
| In the app a file's output is the strip it is on: one of the four pairs, or one of a pair's two outputs when the strip is split (`StripLayout`, `OutputStrip`). One file by itself is a full song on master | Agreed with the user on a sketch, 2026-10-10. A pair and one of its own outputs can then never both be in use. The user's first idea, a 4x4 pad grid like the unit's, was dropped: the app's pads would have been stems where a scene's pads are chunks of every stem |
| A stem file (`.stem.mp4`) is read as its stems: every audio track after the first, named from the JSON in `moov/udta/stem`. The first track, the full mix, is left out, and the file's compressor and limiter settings are not applied (`StemFile`) | The user asked for Traktor's stem files, on the Mac only for now. The stems are what is wanted on the outputs; the mix would only double them |
| The audio of a stem file is decoded by macOS in-process (`AudioToolboxReader`), not by a decoder of our own and not by running `afconvert` | There is no small managed AAC decoder as there was for MP3. In-process needs no temporary files, reports progress, can be cancelled and works under either scripting backend. It is the one place the core depends on an operating system, and it says so (`StemFile.CanRead`) |
| Sample names with layers are label, five characters of the project name and chunk number, 16 characters at most | No longer than a full mix's names, with the label first so that it shows where the unit cuts a name short. Whether same-named samples of two projects can clash on the unit is not known; a full mix's names do not guard against it either |

## 5a. Input formats: what is confirmed

These are about reading audio, not about the SP-16 format.

| Behaviour | Where it is isolated | Evidence |
| --- | --- | --- |
| AIFF and FLAC decode to the same samples as WAV | `AiffReader`, `FlacReader` | Confirmed (file) against Apple's `afconvert`: the fixtures, and the user's recordings converted to AIFF (one) and FLAC (three, one at 24-bit). Other encoders not tried |
| A Layer III decoder's output is 529 samples late | `Mp3Reader.DecoderDelayFrames` | Confirmed (file) on 2026-10-10: a 76-second recording encoded by LAME three ways decodes to the original's length and lines up with it at offset 0 at the start, middle and end (the difference at one sample either way is 2 to 4 times larger). The three fixtures show the same. It is also the figure LAME documents (528 + 1) |
| The delay and padding in an Info or Xing frame are in LAME's layout whatever the encoder's name | `Mp3Reader.ReadTrim` | Confirmed (file) for LAME and for ffmpeg (`Lavc58.35`, `Lavf57.83`): the figures read give the original's length (LAME) and Apple's lengths (ffmpeg) exactly |
| NLayer, with the two fixes, decodes the same audio as LAME's and Apple's decoders | `Assets/NLayer` | Confirmed (file): within one step of 16 bits over the whole of the three LAME encodings above, constant and variable bitrate |

## 6. Open items

- **First real export** (`out/Strands01.tpkg`, from a 71.7 s Traktor recording) was loaded on the SP-16 by the user: it played, and the sound was continuous over the pattern boundaries.
- **That export was 20 ms late and slightly slow.** The analysis at the time gave 93.795 BPM with the lines about 20 ms after the front of each kick. The current analysis gives 93.800 BPM with the first bar line at 0.109 s, and every 4-bar pattern within 2 ms of the beat by `BeatDriftMeter`.
- **Tempo reading of that recording is ambiguous.** The audio has a steady pulse every 0.16 s. The analysis chose 93.795 BPM (the pulse as 16th notes); 125.06 BPM (the pulse as triplets) scored about level in a simpler independent check. Repetition at longer spans favours 93.8. To be settled by ear with the click track.
- **The downbeat is a heuristic** (it credits the beat where the spectrum first changes relative to one bar earlier). Confidence on the test recording was 0.34.
- **First stems export** (`out/Stems112.tpkg`, four stems of a 76 s recording) played on the SP-16 on 2026-10-10. The user's words: "All looks good, the assigned channels switch and there's no glitching, nor over a scene boundary." Asked afterwards, the user confirmed 13 slices on all four stems of the lead-in.
- **The memory limit, measured on 2026-10-10.** The spec had 250 MB as Reported; the user thought 256 MB, and was right in binary megabytes. `HardwareProbes.Memory` packages (distinct 60 s stereo samples, the last cut to fit) of 259, 265 and 268 million bytes of audio loaded in full on the SP-16; 272 and 269 gave "out of memory, could not load sample" and came up with one pad empty, the 18th sample of 26 both times (scene 2, track 2). `Sp16Project.SampleMemoryBytes` is now 268,435,456. Two lock-ups on the way: loading the 265 package with the 259 one loaded, and loading a small project with a large one loaded after leaving USB mass storage mode (which reloads the current project). Each loaded from a fresh start. Mono followed the same day: 140 and 268 million bytes of mono samples loaded in full, so a mono sample costs what its file holds. One file on several tracks is held once: in `Mem268m`, with under half a megabyte free, the user pasted tracks of 60 s samples onto 8 more pads, some from scenes 1 and 2 into scene 4, saved and reloaded without a message. The export never uses a file twice, so nothing changes yet; it is what makes repeat detection worth building. Still open: what decides the lock-ups.
- **Single outputs in 8ch mode**, wanted for mono stems. The strings are known from `route3-mono-8ch.prj` (`AssignTo1` to `AssignTo8`). Both packages of tones from `HardwareProbes.SingleOutputs` were on the SP-16 on 2026-10-10. `SingleOutA.tpkg` (eight stereo samples on outputs 1 to 8): the user heard it correctly, each tone on its output. `SingleOutB.tpkg` (a mono WAV on output 1, on output 2 and on the pair 3-4, a stereo sample on 5-6): "yes sound is emitted as expected". Still open: stem files on Windows, and how to find the right one among Traktor's (its files are named by a code and carry no title).
- **Stems on the master output (2026-10-11).** Built at the user's asking, in the core and as a switch on the Source screen. `out/Master112.tpkg` is the test song's four stems as four tracks on master: 10 patterns in 3 scenes, 51.2 MB. The app's export of it and the command line's (`ExportStems` with `"master,master,master,master"` and stems kept apart) are the same bytes. Waiting for the user to try it on the unit.
- **What counts as a silent sample, and silent patterns at the end (2026-10-13).** A stem's sample is left out when nothing in it comes within 54 dB of the stem's loudest sample, as before, and now also when it is faint throughout (30 dB or more under that peak) with an average level 50 dB or more under it: the click and bleed a separator leaves where an instrument is not playing. Measured on separated stems of a commercial song and the test stems: the samples this adds are at -32/-58, -32/-66, -49/-78 and -35/-54 (loudest/average); the quietest kept is -24/-51. The figures are Claude's, from those two songs. Silence is judged up to where the next chunk starts, not over the tail a sample plays on under the next, and a sample that follows a left-out one starts at full level with no fade in. Patterns at the end of a song that are silent in every layer are dropped, for one file as for stems. Unverified on the unit: nothing made with these has been loaded.
